## What to build

All `unsafe` moves into `rsb-libraw-ffi`, and `rsb-libraw` forbids it. The
ffi crate gains a safe `Processor` that owns a LibRaw instance and exposes
each call the adapter makes as a safe method: open a path, unpack, unpack
the thumbnail, set the output parameters the adapter sets today, process,
and copy out the processed image or thumbnail as an owned `MemImage`
(format, width, height, bits, colors, bytes). LibRaw's return codes reach
the caller as a typed `ErrorCode` inside the ffi crate's one `thiserror`
error enum. The generated bindings stay private: `pub use bindings::*` goes.

`rsb-libraw` keeps the policy: which parameters each decode sets, the
format checks on the processed image, the JPEG thumbnail decode, and the
mapping from `ErrorCode` to `Kind`, including the open-file rule that an
I/O error on a path that exists is `Corrupt`. Its public API and
behaviour do not change.

`rsb-libraw` takes `[lints] workspace = true`, which forbids `unsafe_code`.
`rsb-libraw-ffi` keeps its own lint table without `unsafe_code`. Build
isolation, the dependency edge and the crate names do not change.

LibRaw 0.22.1's `open_file` reads an uninitialised size when `stat`
fails (`LibRaw_bigfile_datastream`'s constructor,
`src/libraw_datastream.cpp:463`), so it reports a missing file as `TooBig`
or `IoError` depending on stack contents. `Processor::open_file` opens the
path for reading first and returns `Error::Open` when that fails, so a
missing or unreadable file does not reach that read; only a file deleted
between our open and LibRaw's stat can. The vendored source is not patched.

LibRaw's `dcraw_make_mem_image` returns unfilled memory when called before
`dcraw_process`, so `Processor` refuses that call itself. Its
`dcraw_make_mem_*` calls report a failed allocation as errno `ENOMEM`,
which `Processor` maps to `InsufficientMemory`.

Metadata (make, model, white balance, color matrix) is not in this
ticket; the linear-decode spec adds it to `Processor`.

When it is done, a reviewer can see every `unsafe` block in one crate, each
with its safety argument, and the compiler refuses `unsafe` anywhere else.

Seams: `Processor` and `MemImage` in `rsb-libraw-ffi`; `RawDecode`.

## Acceptance criteria

- [x] `grep -rn unsafe crates/libraw/src` finds nothing.
- [x] `crates/libraw/Cargo.toml` uses `[lints] workspace = true`, and an `unsafe` block added to `rsb-libraw` fails `cargo check`.
- [x] `rsb-libraw-ffi` exports no bindgen item; `rsb-libraw` uses only `Processor`, `MemImage`, `ImageFormat`, `OutputColor`, `OutputBps`, `ErrorCode` and the ffi `Error`.
- [x] Every `unsafe` block in `rsb-libraw-ffi` outside the generated bindings has a `// SAFETY:` comment, enforced by `clippy::undocumented_unsafe_blocks` in its lint table.
- [x] The 11 unit tests in `adapter.rs` still run: the strerror formatting tests move to the ffi crate, the rest stay and use `ErrorCode`.
- [x] Each LibRaw error constant maps to its own `ErrorCode` variant, and an unknown code maps to `ErrorCode::Other` carrying the code.
- [x] The integration tests in `crates/libraw/tests` pass unchanged.
- [x] Opening a missing file returns `Kind::Io` on every run, and the ffi crate's own test pins `Error::Open` with `NotFound`.
- [x] `engineering/never-crash.md` says `unsafe` is allowed only in `rsb-libraw-ffi` and says the workspace lints forbid `unsafe_code` in `rsb-libraw`; the "review does" sentence is gone.
- [x] The comments above the root and ffi lint tables match the new split; `rsb-libraw` has no table of its own.
- [x] The README's architecture box shows `Processor` in the ffi crate.
- [x] `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass, and the `check` job passes on the PR.
