## What to build

The vendored LibRaw moves from 0.22.1 to 0.22.2 (released 2026-07-16).
0.22.2 is a bugfix-only release, and most of its fixes harden LibRaw
against malformed files: overflows in the CR3 decoder's and
`raw2image`'s allocation sizes, overruns in `parse_phase_one` and
`x3f_parse`, unbounded recursion in `parse_qt` and `parse_mos`, a leak of
stack memory and earlier image metadata between images, and read buffers
zeroed before `fread`. This crate opens whatever file the owner points it
at, so these matter more than anything new in the API.

The vendored tree stays unmodified: it is the 0.22.2 release as
published, under `crates/ffi/vendor/LibRaw-0.22.2/`. The public API and
behaviour of both crates do not change.

0.22.2 does not fix the uninitialised `_fsize` in
`LibRaw_bigfile_datastream`'s constructor; LibRaw's `master` has the fix
(`_fsize(0)` in the initialiser list), so it arrives in the release after
0.22.2. `Processor::open_file` keeps opening the path itself before LibRaw
does. Even after that fix it is the only place a missing or unreadable
file gets a precise `std::io::Error`.

The two LibRaw behaviours `Processor` works around are rechecked against
the 0.22.2 source, and their comments updated to match: the `_fsize` read
above, and `dcraw_make_mem_image` returning an unfilled buffer when called
before `dcraw_process` (`copy_mem_image`'s return code ignored). A third,
`dcraw_make_mem_*` reporting a failed allocation as errno `ENOMEM`, is
rechecked the same way.

The README's "Updating LibRaw" steps gain what this upgrade needed and
they lack: search the repo outside `vendor/` for the old version string
and for line references into LibRaw source, and recheck the workarounds
listed in `Processor`'s comments.

No RAF fixtures exist yet, so "run the full test suite against sample RAW
files" cannot be done here. It is done when the linear-decode tickets
bring fixtures.

Seams: `Processor` in `rsb-libraw-ffi`; `RawDecode`.

## Acceptance criteria

- [x] `crates/ffi/vendor/LibRaw-0.22.2/` holds the same parts of the `0.22.2` release that 0.22.1's tree held (`COPYRIGHT`, `LICENSE.CDDL`, `LICENSE.LGPL`, `README.md`, `internal/`, `libraw/`, `src/`), and `diff -r` of each against a fresh extract shows nothing. `crates/ffi/vendor/LibRaw-0.22.1/` is gone.
- [x] `git grep 0.22.1 -- ':!plan'` finds nothing; `build.rs`, the README's architecture box, "Vendored LibRaw source" section and source link name 0.22.2.
- [x] The bindgen layout assertions compile, so no field `Processor` reads or writes moved.
- [x] Each workaround in `crates/ffi/src/processor.rs` is confirmed still needed in 0.22.2, or removed with its test if not, and each comment that cites LibRaw source cites the 0.22.2 file and line.
- [x] The tests that pin those workarounds pass: missing and unreadable files give `Error::Open`, `make_mem_image` before `dcraw_process` gives `OutOfOrderCall`, and `ENOMEM` gives `InsufficientMemory`.
- [x] The README's "Updating LibRaw" steps include the version-string search and the workaround recheck.
- [x] `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass, and the `check` job passes on the PR.
